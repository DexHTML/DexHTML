# TechRepair

## Внутренняя production-система учёта техники и ремонтов

**Статус:** рабочая внутренняя production-система  
**Этап:** pre-1.0, активный hardening и подготовка к финальному release-аудиту  
**Исходный код:** закрыт

TechRepair — внутренняя web-система для учёта оборудования, его размещения, ремонтов, договоров, актов передачи и подменного фонда.

Проект развивается как самостоятельный источник правды по технике и её ремонтной истории. Он не является заявочной системой: workflow обращений остаётся отдельной зоной ответственности FairDesk.

---

## Что реализовано

- карточки оборудования;
- стабильный код техники;
- QR-идентификация;
- ремонтные циклы и история событий;
- договоры и акты передачи;
- подменный фонд;
- справочники;
- отчёты и XLSX-экспорт;
- пользователи и роли;
- журнал действий;
- read-only API v1 для интеграций.

---

## Надёжность данных и бизнес-логики

За время развития проекта отдельными проверяемыми этапами были закрыты:

- ограничения целостности на уровне базы данных;
- защита от дублей и конкурентных операций;
- транзакционные критичные сценарии;
- защита истории актов и ремонтов от последующего изменения справочных данных;
- контролируемый жизненный цикл подменной техники;
- защита от потерянных обновлений при параллельной работе;
- строгие правила работы с активными и историческими договорами;
- согласованность журнала ремонтов, печатных форм и XLSX;
- защита обязательных системных справочников.

Исторические документы и отчёты используют сохранённые снимки значимых данных там, где последующее изменение справочника не должно менять прошлое.

## Security и эксплуатация

Проект последовательно прошёл отдельные hardening-этапы:

- session hardening;
- idle timeout;
- отзыв активных сессий после изменения авторизации;
- CSRF-защита изменяющих операций;
- stored XSS hardening;
- rate limiting;
- безопасный XLSX export;
- вынесение секретов из репозитория;
- разграничение ролей;
- безопасная обработка непредвиденных ошибок без раскрытия внутренних деталей пользователю.

Production не открывается напрямую в интернет.

---

## Миграции, CI и release-процесс

В проекте используется контролируемая схема изменений:

**feature branch → review → CI → staging proof → merge → post-merge CI → controlled production release → acceptance → documentation closure**

Реализованы:

- versioned database migrations;
- checksum / preflight / verify;
- backup перед миграциями;
- проверка fresh database;
- synthetic restore drill;
- отдельная disposable restore-проверка;
- authenticated HTTP integration tests;
- permanent regression smokes для критичных бизнес-контрактов.

Изменения в production вносятся небольшими изолированными slices, а крупное переписывание работающей системы сознательно не используется.

## Отчёты и аналитика

Отчётность разделяет два разных смысла:

- **состояние на сейчас** — текущая открытая очередь и её возраст;
- **движение за период** — сколько ремонтов пришло, завершилось и осталось открытыми.

Для завершённых ремонтов используются несколько статистических характеристик длительности, включая медиану и P90. Повторные ремонты считаются по фактическим повторным завершённым циклам, а структурные показатели по типам и моделям не выдаются за неподтверждённую частоту отказов.

---

## Интеграционная роль

TechRepair остаётся source of truth по оборудованию.

Для внешних внутренних модулей используется стабильный код техники и read-only API. Интеграция строится так, чтобы другие системы могли получить карточку оборудования, но не менять состояние TechRepair без отдельно утверждённого write-контракта.

В общей архитектуре:

- **TechRepair** — техника и ремонтная история;
- **FairDesk** — заявки и workflow;
- **Duty Schedule** — доступность сотрудников;
- **ServiceHub** — будущая общая точка входа.

## Ограничения

- система предназначена для внутренней сети;
- исходный код и production-данные закрыты;
- это решение для конкретного рабочего процесса, а не публичный SaaS;
- внешний write API не является частью текущего контракта;
- финальный путь к версии 1.0 ещё не завершён.

Публичный case study намеренно не содержит внутренних адресов, production-данных, секретов и идентифицирующей информации.
